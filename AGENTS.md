# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## SAC Flow engineering contract

During active development, all work is local-only. Do not push to GitHub, publish a Sites version, deploy externally, or write to Metricool unless the user gives explicit authorization for that exact action. Metricool writes include account records, connected accounts, configuration, messages, replies, tokens, automation state, and any other operation that changes the remote account.

The product direction is now a general automation platform inspired by the functional breadth of n8n, with the SAC/Metricool experience preserved as the primary first-party workspace and the most prominent operational module. Study n8n architecture and behavior as reference, but keep this implementation original and respect n8n licensing boundaries; do not copy Enterprise Edition source.

SAC Flow is a local-first SAC MVP for approximately 20 Instagram/Facebook brands accessed through Metricool. Keep the web client in `src/` and the Fastify boundary in `server/`. Browser code must call the internal `/api` contract; it must never call Metricool directly or receive Metricool credentials.

Runtime and deployment must be self-contained. Codex skills, plugins and research helpers—including Agent Reach/Exa—may inform development, but must never become application dependencies, runtime services, build requirements, Docker components or production integrations.

The default developer experience is one command (`npm run dev:all`): Vite on 5173 proxies `/api` to Fastify on 8787. The production/container experience is one Fastify process on 8787 with `SERVE_FRONTEND=true`, serving `dist/client` and preserving API 404s instead of returning the SPA shell for `/api/*`.

Production keeps the `backup` service in `docker-compose.production.yml` (`scripts/postgres-backup.sh`): a daily `pg_dump` outside the Docker volume with retention, a failed backup never deletes older ones, and restore runs in a single transaction only with explicit confirmation and the API stopped. Keep Metricool behind an adapter and local JSON behind a repository interface so Techlab can replace JSON with PostgreSQL and move polling to workers without changing the frontend contract. JSON writes must remain serialized and atomic. Use stable external IDs for deduplication and idempotency; never treat Excel as persistence.

Demo mode must work with fictitious seeded data and without credentials. Live mode must be explicit. Never add tokens, real `userId`/`blogId` values, DMs, comments, email addresses, phone numbers or customer identifiers to tracked files, fixtures, screenshots, logs or XLSX samples.

Preserve provider limits in code and UI: Metricool API requires Advanced/Custom; Instagram exposes the main inbox only; comments on ads cannot be answered; Metricool informa plazos de 24 horas para comentarios y 7 días para DMs. La UI debe permitir siempre redactar, guardar e intentar una respuesta manual, advertir cuando esté fuera de plazo y dejar que Metricool/Meta decidan la aceptación final; no agregues comportamiento destinado a eludir esos límites.

Automatic sending is off by default. Automatic sending must reject ineligible/out-of-window items, every attempt must be auditable, and retries must avoid duplicate replies. An agent may manually attempt an old reply with explicit confirmation; sensitive or negative cases must remain eligible for human review.

The visual system is the same CSS as WiwoLab (`apps/web/src/app/globals.css`, its shared Tailwind preset and the classes of its shell, rail, home, button, select and confirm components), by the user's request; it lives in `src/styles/wiwolab.css`, loaded after `src/styles.css`, which maps the wiwo.sac tokens onto Lab's values. Dark mode is the default: `#121212` canvas with Lab's drifting green/blue aurora, solid `#212121` cards with `#333` hairline borders, 16px radius and Lab's soft shadow, `#F7F7F3` ink, `#A3A3A3` muted text, primary `#6161FF`. A header toggle switches to light mode (`modo normal`: `#FDFDFB` canvas, white cards, `#E9E8E1` borders, `#1F1F1F` ink, primary `#4242FF`), persisted per browser. Primary actions are Lab's green pill (`#3BFF00`, `#43FF0A` in dark, always with `#292929` ink), secondary actions are outline pills, destructive actions solid red; icon buttons are 40px round without border; the profile avatar is a 32px primary circle; fields are 12px-radius on the page color with a primary border on focus; confirmations use Lab's dialog (page-colored panel, `Cancelar` on the muted fill, blue or red action). Scrollbars stay hidden, as in Lab. New styles must use these tokens instead of hardcoded colors, and visual changes should stay aligned with WiwoLab. The slim icon rail and the centered `wiwo.sac` wordmark (`src/assets/wiwo-sac-logo.png`: the original bold WIWO `wiwo.` followed by a light lowercase Outfit `sac` sized to the bold x-height, with tight spacing around the period, as in the old `wiwo.Nodes` lockup; the user chose it over `sac.wiwo`, `wiwo.SAC` and `wiwo.Sac`) stay. The product name is `wiwo.sac` (lowercase, in that order, never `WIWO.SAC` nor `sac.wiwo`; it was briefly `sac.wiwo` before the user settled on `wiwo.sac`) in every visible text, title and document; internal identifiers that predate the rename (the `wiwo_nodes_session` cookie, `wiwo-nodes*` browser storage keys, `nodesRole`/`nodesBrandIds`, the repository and deploy paths) stay as they are so sessions and saved preferences survive. The favicon follows the wiwo.Me icon family: a square `#4242FF` tile with the hand-drawn black word `SAC` (`public/favicon.svg`, with `favicon.ico` and `apple-touch-icon.png` rendered from it; regenerate both when the SVG changes). The Home hero greets the signed-in user by time of day and first name (`Buenos días, <nombre>` with the animated WIWO gradient on the name and the WIWO orb), falling back to the salutation alone for role placeholders such as `Administrador local`; the operational headline `Lo que necesita atención, primero.` stays directly below it. As in Lab's home, the greeting sits on the page without a card and ends with the short green-to-blue gradient band before its actions. Do not reintroduce orange or warm peach accents; reserve green/red/amber for meaningful success/risk/warning states, except that neon green is also Lab's primary-action color and a brand highlight. The sign-in screen mirrors the WiWO Ops login anatomy and stays dark regardless of the app theme: the illustrated spring scene behind a dark brand veil, the beige `wiwo.sac` wordmark, the full WIWO Thinking Orb and the tagline `Mensajes, Cuentas y Automatizaciones. / Un solo lugar.` on the left, and a glass `Entrar` panel on the right with only the `Iniciar sesión con Google` button (Google mark in a white circle on the left of a dark pill; no email/password option in production, the form exists only in the local test mode `SAC_FLOW_AUTH_MODE=dev`). Sign-in is Google OAuth handled by the Fastify server against a local allowlist; Firebase is not used, and the Google client secret must never reach the browser or tracked files. The profile menu (avatar top-right) holds name, email, identity and role chips, and `Cerrar sesión`; the rail has no separate help or profile buttons. `Credenciales` and `Usuarios y roles` are admin-only in both the rail and the API. The rest of the rail is filtered by permission (`VIEW_PERMISSIONS` in `src/App.tsx`, any one permission shows the section): agents see only Inicio and the three inbox views; Resumen SAC and Reportes need `metrics.read`, Flujo SAC and Configuración need `workflow.edit` (or `workflow.publish` for the flow), Cuentas needs `brands.manage` or `metrics.read`, and Automatización/Ejecuciones/Plantillas need `automations.edit`; Home hides shortcuts to sections the person cannot open and adapts to the role: agents get their own in-window cases, a due-in-24h tile and `Tomar siguiente`; supervisors (`metrics.read` or `inbox.assign_others`) get the `Equipo` workload panel; admins also get the `Sistema` panel (last Metricool sync, auto-reply state, failed jobs). Each `Equipo` row (a person or `Sin asignar`) is a button that opens the Bandeja filtered by that responsible person (`Asignación → Responsable`, value `user:<userId>`, only for `canSeeTeam` roles; agents never get it) with the `Por atender en plazo` deadline filter (pending or human review, inside the window), so the Bandeja count equals the panel's; a chip next to the total removes it. Controls a role cannot use are hidden rather than shown disabled. `Reportes` is part of the monthly-report workflow (the site is also where monthly SAC metrics are pulled): it shows the `buildSacReport` figures per brand and month (UTC days) with data-quality warnings and the month's Excel. There is no PPTX template, so the web does not generate presentations or close months. Metricool brings TikTok (Business accounts) and LinkedIn comments, which flow through the Bandeja and `Gestión comentarios` like any other network, but not their DMs nor the history kept in the team's spreadsheets: `Reportes` → `Cargar TikTok/LinkedIn` (permission `records.import`, default Supervisor and Admin) uploads the brand's BD SAC Excel (`POST /api/brands/:brandId/manual-records`, review first with `dryRun`, then save; `server/manual-records.ts`), stored as inbound interactions with `source: "planilla"` and a manual `sacTriage`; they count in Reportes, the Excel and the METRIQ integration routes but never in the inbox, Home or `stats/summary` (`operationalInteractionFilters` excludes `planilla`), and re-uploading never duplicates (deterministic `externalId` plus text match against what Metricool already brought for that network). Only master admins (`SAC_FLOW_AUTH_ADMIN_EMAILS`) can hide or show a client (`PUT /api/brands/:brandId/visibility`, `brand.active`/`account.active`; an in-app assigned admin gets `403 MASTER_ADMIN_REQUIRED`); a hidden client stops syncing and disappears from the inbox, Home, Reportes, METRIQ and, for everyone except master admins, from `GET /api/brands`, keeping all its history for when it is shown again. Whether a message is an SAC case or social noise is decided by the no-AI rules (`esCasoSac` in `server/sac-report.ts`, based on `esMensajeGestionado`) unless a person marked it (`PUT /api/interactions/:id/triage`, bulk `POST /api/interactions/triage`, stored as `sacTriage.modelo = "manual"`); manual marks always win and bulk marking never overwrites them. AI classification runs only in shadow mode (`docs/PROPUESTA_IA.md`, phase 1): off by default (`SAC_FLOW_AI_ENABLED=false`), the provider sits behind an adapter (`server/ai-provider.ts`; default DeepSeek on BytePlus ModelArk through its OpenAI-compatible API with `BYTEPLUS_API_KEY`, alternative Claude), only brands listed in `SAC_FLOW_AI_BRAND_IDS` send text, and every text is masked first (`server/ai-redaction.ts`: emails, phones, RUT, cards, @users, links; never names, handles or Metricool references). The worker (and `scripts/classify-interactions.mjs`) writes only `aiTriage` (`server/ai-shadow-triage.ts`, column `interactions.ai_triage`): never `sacTriage`, category, sentiment, confidence, status or version, never over a manual mark, and it does not count in Reportes until its agreement with manual marks (`GET /api/ai/agreement`) justifies promoting it. Its `sensible` flag can only add human review (`AI_SENSITIVE_SIGNAL`, `requiresHumanReview`, `isSensitiveCase`), never remove it. The inbox detail's `Recomendación de respuesta con IA` (Bandeja panel and Gestión DMs/comentarios, `src/components/AiReplySuggestion.tsx`) really uses AI: `POST /api/interactions/:id/ai/draft` (`server/ai-reply-draft.ts`, permission `inbox.reply`) asks the same provider for a suggestion grounded only in the brand's approved, unexpired QA for that channel, plus the masked thread and post text; the model writes `{nombre}` and the server fills the first name, so names and handles never leave. It is requested when an open inbound case is shown, cached server-side per exact context (reopening costs nothing; `Otra sugerencia` regenerates), never writes the case, its version, a draft or Metricool, and only reaches the composer through `Usar recomendación`. Numbers, links, emails and accounts not found in the cited QA or the customer's own text are flagged as warnings, delicate cases are marked for human judgment, and when AI is off or the brand is not authorized (`GET /api/ai/availability`) the box falls back to the rule-based template labeled `Respuesta sugerida por reglas`. AI output never sends or enables automatic replies, and the provider key never reaches the browser, logs, tests or tracked files. Spam and noise are flagged, never removed automatically: `server/noise-detection.ts` (pure, over the lists the inbox, post comments and Reportes already load) marks comments repeated 3+ times by one account, the same long comment from 3+ accounts within 72 h, mentions-only comments, promotional or Meta-impersonation scams (also in DMs; repetition rules never apply to DMs, where a customer insisting is not spam), and the shadow AI's `aiTriage.ruido` (`spam_promocional`, `estafa_phishing`, prompt `sac-triage-v3`). The signal travels as `noise` on public interactions, `noiseCount` on contacts and `noisePendingCount` on posts; reply targets and the post work queue put flagged items last. The Bandeja `Spam` filter hides rule-detected spam by default (AI-only suggestions stay visible with their label; the Home `Equipo` focus shows everything so counts match), and Gestión comentarios shows the count per post and a per-post discard. Discarding is a person's decision: `POST /api/interactions/discard-noise` (dry run first, `inbox.triage` plus `inbox.assign_others`, confirmed in the in-app dialog) resolves the open flagged cases with reason `spam` and a manual noise triage, skips sensitive and manually-kept cases, never touches Metricool and stays reopenable. Reportes stops counting rule-detected noise as cases unless manually marked (`clasificacion.spam`), and a mention (`@cuenta`) is never counted as a word of the message. Admins assign roles in-app (`Usuarios y roles`, persisted in `user_access`); `SAC_FLOW_AUTH_ADMIN_EMAILS` stays the locked master key and nobody can change their own role. Only those master admins can grant the Admin role, change another admin, or create/edit/reset roles; admins assigned in-app ("admin asignado") see the Roles tab read-only and can never grant `MASTER_ONLY_PERMISSIONS` (`brands.manage`, `automations.edit`, `workflow.publish`, `inbox.archive_expired`, `export.xlsx`) to someone who lacks them, neither via personal adjustments nor by assigning a role that carries them; removing or downgrading stays allowed. Roles are editable permission sets (`server/permissions.ts`, stored in `access_roles`): Lector/Agente/Supervisor can be adjusted and reset, custom roles can be created from a template, Admin is fixed with everything, a person can carry personal permission adjustments on top of their role (stored as added/removed keys, edited from the person drawer), and administration (users and roles, credentials, enabling automatic sending, security audit, job retries) is never delegable. API routes check permissions with `requirePermission`; the UI gates controls with `can()` from `src/lib/permissions.ts`. The login orb comes from WiWO Ops (`src/styles/wiwo-orb.css`, its inner rules scoped under `.orbe-wiwo`) and the scene from `src/assets/login-escena-primavera.html`; every other orb is WiwoLab's Thinking Orb (`src/components/ThinkingOrb.tsx` with `src/styles/thinking-orb.css`, a copy of Lab's file with the volumetric rules scoped under `.wiwo-orb-stage` so the two never mix). Loading states never use spinners: the session check and section loads (Centro SAC, Automation Studio, workflow editor) show `OrbLoader`, Lab's aura orb with `Cargando…`; panels that load (conversation, posts, operational queue, home queue) show the orb in place of their icon; busy buttons and in-progress notices show the small generating orb (`BusyOrb`); only the Google sign-in button keeps a spinner, as in Lab's login; browser autofill must never repaint the fields light. Confirmations never use browser dialogs (`window.confirm`/`alert`/`prompt`): call `confirmAction()` from `src/lib/confirm.ts`, rendered by the in-app `ConfirmHost` glass dialog (danger tone for deactivating, removing access or discarding work, with focus starting on Cancelar). Every view must be usable at the browser default zoom on common laptop and desktop sizes (from ~1093×614 effective up to 1920×1080) without the operator zooming: no fixed minimum heights that push content below the viewport, `Gestión DMs/comentarios` fills exactly the visible height with internal scrolling and the composer actions always visible, and body text never below ~9.5px.

The default Home is a SAC operations center, not a generic automation landing page. Keep `Centro de operaciones SAC` and the operational hierarchy: actionable conversation queue, human review, unassigned work, account health and SAC flow state first; general automation inventory second. Never show a success percentage when there are zero executions, and never hardcode an environment such as production without verified runtime evidence. Home counts actionable work only while it is inside the Meta reply window (7 days DMs, 24 hours comments, from the customer's last message) and reports out-of-window cases separately; while the first load is in flight it shows placeholders, never zeros. The Bandeja hides expired cases by default (Plazo filter) and sorts actionable work by time left; it offers `Tomar siguiente` (claims and opens the soonest in-window unassigned case), a `Mis casos` filter, a searchable account filter with in-window counts, J/K/R/E shortcuts and `Siguiente caso` in the detail, per-browser remembered filters, a `(N)` new-case count in the tab title, and card rows with collapsible filters on phones; expired cases can be archived in bulk as history (permission `inbox.archive_expired`, never sensitive cases, never touching Metricool). Gestión DMs/comentarios lists accounts by in-window pending work and opens the busiest one once, never switching accounts on its own afterwards.

The SAC inbox detail is the operator's primary workspace. The detail opens as a side panel over a blurred backdrop; a click outside closes it, asking first only when the reply has unsaved changes. Keep the complete inbound message, an optional chronological conversation history, a clearly labeled AI recommendation grounded in approved brand QA, and one editable response composer together in the same side panel. Clearing a draft must never delete the customer's remote message. Each brand must also have an organized document center with a records workbook, a separate approved-QA workbook, and categorized shared file links.

Keep two complementary SAC inbox experiences. `Bandeja SAC` remains the contact-centric triage, protocol, bulk-draft and export surface and must not be simplified as part of manual-workspace changes. `Gestión manual` is an account-first workspace inspired by the supplied Meta Business Suite reference: channel/type tabs above two simultaneous zones for queue and active conversation/composer. Keep required post context inline with the active conversation instead of adding a separate right rail. Adapt that operational anatomy to the wiwo.sac blue design system; never replace the existing inbox or enable automatic sending from the manual workspace.

Within `Gestión manual`, comment surfaces are post-centric. List one card per publication, order posts newest-to-oldest by the provider-supplied publication timestamp, and label the fallback honestly when only recent comment activity is available. Opening a post must load its exact unanswered inbound comments without mixing posts, order that work queue oldest-to-newest for SLA, and bind every manual action to the selected comment ID and version. The open chat or post shows who has it in charge (`A cargo:` next to the status; for a post, the owners of its open comments; the viewer reads as `Tú`), as the Bandeja SAC does.

The SAC inbox list is contact-centric: show one row per verified person within the same account and social platform, with message and pending counts, while every operation remains bound to the exact inbound interaction being answered. Keep this visual person identity separate from the strict provider thread key used by reconciliation and automation. For comments, the response panel must show the provider-supplied post context and original-post link when available; never fabricate a permalink from a social ID.

A later outbound message closes an inbound case as `Respondido por el equipo` (`reconcileConversationResponses` in `server/sac-automation.ts`), except automatic greetings: the same outbound text sent by the account in at least 3 conversations within 60 seconds of the customer's message never closes a case. A closed case can always be reopened from the UI (`Reabrir caso`, status `pending` with reason `reopened`, permission `inbox.triage`), which targets the customer's latest inbound message and keeps it open against earlier account replies.

Keep inbox freshness separate from response automation. A dedicated read-only worker may ingest Metricool on its configured interval while the visible inbox rereads local persistence in the background; neither action authorizes an outbound message. Show the last local view refresh separately from the last confirmed Metricool synchronization, and keep a manual `Actualizar ahora` action for an operator-triggered read sync. The inbox is live in every view: the API wraps the repository (`server/inbox-live.ts`) to log which interactions each revision changed, pushes revisions over `GET /api/inbox/stream` (SSE, revision only, never case data) and serves per-actor deltas from `GET /api/inbox/changes`; the client merges changed contact rows instead of reloading everything, falls back to 10 s polling when the stream does not arrive, does a full reload every 10 minutes, and recomputes reply-window counts every minute. New interaction writes must go through the repository methods so they are tracked. `Gestión DMs/comentarios` is chat-like: while it is open and visible it reads the open account's surface from Metricool every 15 s (`POST /api/sync/live`, read-only, throttled server-side to once per 10 s per account and surface, no run recorded, never waiting on the portfolio sync lock) and `Actualizar cuenta` uses the same fast read; the open conversation refreshes by itself, a reply sent from wiwo.sac shows once even after Metricool syncs it back, and the header shows `En vivo · revisado hh:mm:ss`. An answered DM never locks the composer: the person can keep writing to the same conversation (`followUp: true` on the reply, one new delivery per message, Ctrl/Cmd+Enter sends; an emoji button inside the field (`src/components/EmojiPicker.tsx`, a short built-in list without dependencies, recent emojis remembered per browser) inserts at the cursor; the in-app confirmation appears only on the first send to each conversation per browser session, by the user's explicit request), the open chat follows the customer to their newest message when it arrives (unless there is unsent text) and refreshes for the brand's chatbot replies (the detail carries its `contactKey` from the conversation response), the chat opens on the customer's latest message (`latestInboundId`), and the composer starts empty because `responseText` there is what was already sent. Resolved cases, comments and cases with an active or uncertain delivery stay locked.

When changing routes, response fields, environment variables, persistence shape, ports or operational behavior, update `.env.example`, `README.md`, `docs/API_CONTRACT.md`, and the relevant runbook in the same change. Before handoff run `npm run check`, `npm run build:all`, then `npm test`, followed by the Docker health smoke test; report commands and outputs, not assumptions.
