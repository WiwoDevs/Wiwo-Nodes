# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## SAC Flow engineering contract

During active development, all work is local-only. Do not push to GitHub, publish a Sites version, deploy externally, or write to Metricool unless the user gives explicit authorization for that exact action. Metricool writes include account records, connected accounts, configuration, messages, replies, tokens, automation state, and any other operation that changes the remote account.

The product direction is now a general automation platform inspired by the functional breadth of n8n, with the SAC/Metricool experience preserved as the primary first-party workspace and the most prominent operational module. Study n8n architecture and behavior as reference, but keep this implementation original and respect n8n licensing boundaries; do not copy Enterprise Edition source.

SAC Flow is a local-first SAC MVP for approximately 20 Instagram/Facebook brands accessed through Metricool. Keep the web client in `src/` and the Fastify boundary in `server/`. Browser code must call the internal `/api` contract; it must never call Metricool directly or receive Metricool credentials.

Runtime and deployment must be self-contained. Codex skills, plugins and research helpers—including Agent Reach/Exa—may inform development, but must never become application dependencies, runtime services, build requirements, Docker components or production integrations.

The default developer experience is one command (`npm run dev:all`): Vite on 5173 proxies `/api` to Fastify on 8787. The production/container experience is one Fastify process on 8787 with `SERVE_FRONTEND=true`, serving `dist/client` and preserving API 404s instead of returning the SPA shell for `/api/*`.

Keep Metricool behind an adapter and local JSON behind a repository interface so Techlab can replace JSON with PostgreSQL and move polling to workers without changing the frontend contract. JSON writes must remain serialized and atomic. Use stable external IDs for deduplication and idempotency; never treat Excel as persistence.

Demo mode must work with fictitious seeded data and without credentials. Live mode must be explicit. Never add tokens, real `userId`/`blogId` values, DMs, comments, email addresses, phone numbers or customer identifiers to tracked files, fixtures, screenshots, logs or XLSX samples.

Preserve provider limits in code and UI: Metricool API requires Advanced/Custom; Instagram exposes the main inbox only; comments on ads cannot be answered; Metricool informa plazos de 24 horas para comentarios y 7 días para DMs. La UI debe permitir siempre redactar, guardar e intentar una respuesta manual, advertir cuando esté fuera de plazo y dejar que Metricool/Meta decidan la aceptación final; no agregues comportamiento destinado a eludir esos límites.

Automatic sending is off by default. Automatic sending must reject ineligible/out-of-window items, every attempt must be auditable, and retries must avoid duplicate replies. An agent may manually attempt an old reply with explicit confirmation; sensitive or negative cases must remain eligible for human review.

The approved visual direction follows the WIWO product family (wiwo.Me, MetriQ, Lab) and its shared CSS tokens: `--wiwo-blue #4242FF`, `--wiwo-green #3BFF00`, `--wiwo-purple #8D7CFF`, `--wiwo-beige #F8FAD7`, the green-to-blue `--wiwo-gradient-primary`, Plus Jakarta Sans, and `wiwo-glass` surfaces (translucent fill, hairline stroke, 22px backdrop blur). Dark mode is the default: `#121212` canvas with subtle green/blue aurora glows, beige ink, blue gradient pill for the active rail item and primary actions, round glass icon buttons. A header toggle switches to light mode (`modo normal`: `#FDFDFB` canvas, `#292929` ink), persisted per browser; both modes share the tokens in `src/styles.css` (`:root` and `:root[data-theme="light"]`), so new styles must use those tokens instead of hardcoded colors. The slim icon rail and the centered `wiwo.Nodes` wordmark stay. The Home hero greets the signed-in user by time of day and first name (`Buenos días, <nombre>` with the animated WIWO gradient on the name and the WIWO orb), falling back to the salutation alone for role placeholders such as `Administrador local`; the operational headline `Lo que necesita atención, primero.` stays directly below it. Do not reintroduce orange or warm peach accents; reserve green/red/amber for meaningful success/risk/warning states, with neon green also allowed as a sparing brand highlight. The sign-in screen mirrors the WiWO Ops login anatomy and stays dark regardless of the app theme: the illustrated spring scene behind a dark brand veil, the beige `wiwo.Nodes` wordmark, the full WIWO Thinking Orb and the tagline `Mensajes, Cuentas y Automatizaciones. / Un solo lugar.` on the left, and a glass `Entrar` panel on the right with only the `Iniciar sesión con Google` button (Google mark in a white circle on the left of a dark pill; no email/password option in production, the form exists only in the local test mode `SAC_FLOW_AUTH_MODE=dev`). Sign-in is Google OAuth handled by the Fastify server against a local allowlist; Firebase is not used, and the Google client secret must never reach the browser or tracked files. The profile menu (avatar top-right) holds name, email, identity and role chips, and `Cerrar sesión`; the rail has no separate help or profile buttons. `Credenciales` and `Usuarios y roles` are admin-only in both the rail and the API. The rest of the rail is filtered by permission (`VIEW_PERMISSIONS` in `src/App.tsx`, any one permission shows the section): agents see only Inicio and the three inbox views; Resumen SAC and Reportes need `metrics.read`, Flujo SAC and Configuración need `workflow.edit` (or `workflow.publish` for the flow), Cuentas needs `brands.manage` or `metrics.read`, and Automatización/Ejecuciones/Plantillas need `automations.edit`; Home hides shortcuts to sections the person cannot open and adapts to the role: agents get their own in-window cases, a due-in-24h tile and `Tomar siguiente`; supervisors (`metrics.read` or `inbox.assign_others`) get the `Equipo` workload panel; admins also get the `Sistema` panel (last Metricool sync, auto-reply state, failed jobs). Controls a role cannot use are hidden rather than shown disabled. `Reportes` is part of the monthly-report workflow (the site is also where monthly SAC metrics are pulled): it shows the `buildSacReport` figures per brand and month (UTC days) with data-quality warnings and the month's Excel. There is no PPTX template, so the web does not generate presentations or close months. AI classification is not active for now: whether a message is an SAC case or social noise is decided by the no-AI rules (`esCasoSac` in `server/sac-report.ts`, based on `esMensajeGestionado`) unless a person marked it (`PUT /api/interactions/:id/triage`, bulk `POST /api/interactions/triage`, stored as `sacTriage.modelo = "manual"`); manual marks always win and bulk marking never overwrites them. Admins assign roles in-app (`Usuarios y roles`, persisted in `user_access`); `SAC_FLOW_AUTH_ADMIN_EMAILS` stays the locked master key and nobody can change their own role. Only those master admins can grant the Admin role, change another admin, or create/edit/reset roles; admins assigned in-app ("admin asignado") see the Roles tab read-only and can never grant `MASTER_ONLY_PERMISSIONS` (`brands.manage`, `automations.edit`, `workflow.publish`, `inbox.archive_expired`, `export.xlsx`) to someone who lacks them, neither via personal adjustments nor by assigning a role that carries them; removing or downgrading stays allowed. Roles are editable permission sets (`server/permissions.ts`, stored in `access_roles`): Lector/Agente/Supervisor can be adjusted and reset, custom roles can be created from a template, Admin is fixed with everything, a person can carry personal permission adjustments on top of their role (stored as added/removed keys, edited from the person drawer), and administration (users and roles, credentials, enabling automatic sending, security audit, job retries) is never delegable. API routes check permissions with `requirePermission`; the UI gates controls with `can()` from `src/lib/permissions.ts`. Orb styles come from WiWO Ops (`src/styles/wiwo-orb.css`) and the scene from `src/assets/login-escena-primavera.html`; browser autofill must never repaint the fields light. Confirmations never use browser dialogs (`window.confirm`/`alert`/`prompt`): call `confirmAction()` from `src/lib/confirm.ts`, rendered by the in-app `ConfirmHost` glass dialog (danger tone for deactivating, removing access or discarding work, with focus starting on Cancelar). Every view must be usable at the browser default zoom on common laptop and desktop sizes (from ~1093×614 effective up to 1920×1080) without the operator zooming: no fixed minimum heights that push content below the viewport, `Gestión DMs/comentarios` fills exactly the visible height with internal scrolling and the composer actions always visible, and body text never below ~9.5px.

The default Home is a SAC operations center, not a generic automation landing page. Keep `Centro de operaciones SAC` and the operational hierarchy: actionable conversation queue, human review, unassigned work, account health and SAC flow state first; general automation inventory second. Never show a success percentage when there are zero executions, and never hardcode an environment such as production without verified runtime evidence. Home counts actionable work only while it is inside the Meta reply window (7 days DMs, 24 hours comments, from the customer's last message) and reports out-of-window cases separately; while the first load is in flight it shows placeholders, never zeros. The Bandeja hides expired cases by default (Plazo filter) and sorts actionable work by time left; it offers `Tomar siguiente` (claims and opens the soonest in-window unassigned case), a `Mis casos` filter, a searchable account filter with in-window counts, J/K/R/E shortcuts and `Siguiente caso` in the detail, per-browser remembered filters, a `(N)` new-case count in the tab title, and card rows with collapsible filters on phones; expired cases can be archived in bulk as history (permission `inbox.archive_expired`, never sensitive cases, never touching Metricool). Gestión DMs/comentarios lists accounts by in-window pending work and opens the busiest one once, never switching accounts on its own afterwards.

The SAC inbox detail is the operator's primary workspace. Keep the complete inbound message, an optional chronological conversation history, a clearly labeled AI recommendation grounded in approved brand QA, and one editable response composer together in the same side panel. Clearing a draft must never delete the customer's remote message. Each brand must also have an organized document center with a records workbook, a separate approved-QA workbook, and categorized shared file links.

Keep two complementary SAC inbox experiences. `Bandeja SAC` remains the contact-centric triage, protocol, bulk-draft and export surface and must not be simplified as part of manual-workspace changes. `Gestión manual` is an account-first workspace inspired by the supplied Meta Business Suite reference: channel/type tabs above two simultaneous zones for queue and active conversation/composer. Keep required post context inline with the active conversation instead of adding a separate right rail. Adapt that operational anatomy to the WIWO.Nodes blue design system; never replace the existing inbox or enable automatic sending from the manual workspace.

Within `Gestión manual`, comment surfaces are post-centric. List one card per publication, order posts newest-to-oldest by the provider-supplied publication timestamp, and label the fallback honestly when only recent comment activity is available. Opening a post must load its exact unanswered inbound comments without mixing posts, order that work queue oldest-to-newest for SLA, and bind every manual action to the selected comment ID and version.

The SAC inbox list is contact-centric: show one row per verified person within the same account and social platform, with message and pending counts, while every operation remains bound to the exact inbound interaction being answered. Keep this visual person identity separate from the strict provider thread key used by reconciliation and automation. For comments, the response panel must show the provider-supplied post context and original-post link when available; never fabricate a permalink from a social ID.

Keep inbox freshness separate from response automation. A dedicated read-only worker may ingest Metricool on its configured interval while the visible inbox rereads local persistence in the background; neither action authorizes an outbound message. Show the last local view refresh separately from the last confirmed Metricool synchronization, and keep a manual `Actualizar ahora` action for an operator-triggered read sync. The inbox is live in every view: the API wraps the repository (`server/inbox-live.ts`) to log which interactions each revision changed, pushes revisions over `GET /api/inbox/stream` (SSE, revision only, never case data) and serves per-actor deltas from `GET /api/inbox/changes`; the client merges changed contact rows instead of reloading everything, falls back to 10 s polling when the stream does not arrive, does a full reload every 10 minutes, and recomputes reply-window counts every minute. New interaction writes must go through the repository methods so they are tracked.

When changing routes, response fields, environment variables, persistence shape, ports or operational behavior, update `.env.example`, `README.md`, `docs/API_CONTRACT.md`, and the relevant runbook in the same change. Before handoff run `npm run check`, `npm run build:all`, then `npm test`, followed by the Docker health smoke test; report commands and outputs, not assumptions.
